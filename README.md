# Giganto: Raw-Event Storage System for AICE

Giganto is a high-performance raw-event storage system, specifically designed
for AICE. It is optimized to receive and store raw events through QUIC channels
and provides a flexible GraphQL API for querying the stored events. Giganto
empowers AICE with the ability to efficiently handle large-scale data processing
and real-time analytics.

[![Coverage Status](https://codecov.io/gh/aicers/giganto/branch/main/graph/badge.svg)](https://codecov.io/gh/aicers/giganto)

## Features

- Scalable Storage: Giganto provides a scalable and distributed storage system,
  optimized for handling raw events generated by AICE sensors.
- GraphQL API: Giganto offers a powerful and flexible GraphQL API, enabling
  developers to query stored events with ease.
- QUIC Channels: Giganto utilizes the QUIC protocol to enable fast, low-latency
  communication and data transfer.
- High Performance: Giganto is designed to efficiently handle high volumes of
  data, ensuring optimal performance for AICE.

## Usage

You can run Giganto by invoking the following command:

```sh
giganto -c <CONFIG_PATH> --cert <CERT_PATH> --key <KEY_PATH> --ca-certs \
<CA_CERT_PATH>[,<CA_CERT_PATH>,...]
```

### Arguments

<!-- markdownlint-disable MD013 -->
| Name             | Description                          | Required |
| ---------------- | ------------------------------------ | -------- |
| `<CONFIG_PATH>`  | Path to the TOML configuration file. | Yes      |
| `<CERT_PATH>`    | Path to the certificate file.        | Yes      |
| `<KEY_PATH>`     | Path to the private key file.        | Yes      |
| `<CA_CERT_PATH>` | Path to the CA certificates file.    | Yes      |
<!-- markdownlint-enable MD013 -->

#### Certificates

Every certificate — Giganto's own, cluster peers', and ingest and publish
clients' — must carry a SAN DNS name of the form
`<instance>.<service>.<host>.<domain>` (for example,
`001.giganto.node1.example.com`). Giganto reads its identities from this SAN and
rejects a certificate that does not carry one. Bootroot issues such certificates
in production; for tests, static certificates from any CA work as long as they
carry the SAN.

#### Notes on Arguments

- The `--ca-certs` argument accepts multiple values, separated by commas. You
  can also repeat the argument to specify multiple CA certificates.

#### Logging

Giganto writes its log to standard output. `RUST_LOG` sets the level (default
`info`).

When standard output or standard error is connected to the systemd journal
(`JOURNAL_STREAM`), each event is one line that starts with its syslog priority
(`<3>` error, `<4>` warning, `<6>` info, `<7>` debug and trace), without a
timestamp or colour codes, with line breaks inside an event written as `\n`, and
a panic is logged as one error entry. Elsewhere colour codes are written only to
a terminal.

`--log-path` was removed; a command line that passes it is refused at startup.

### Example

- Run Giganto with local configuration file and multiple CA certificates.

```sh
giganto -c path/to/config.toml --cert /path/to/cert.pem --key /path/to/key.pem \
--ca-certs /path/to/ca_cert1.pem,/path/to/ca_cert2.pem
```

- Run Giganto from source.

```sh
cargo run -- -c path/to/config.toml \
--cert /path/to/cert.pem \
--key /path/to/key.pem --ca-certs /path/to/ca_cert1.pem,/path/to/ca_cert2.pem
```

## Configuration

In the config file, you can specify the following options:

<!-- markdownlint-disable MD013 -->

| Field                  | Description                          | Required | Default               |
| ---------------------- | ------------------------------------ | -------- | --------------------- |
| `ingest_srv_addr`      | Address to listen for ingest QUIC    | No       | [::]:38370            |
| `publish_srv_addr`     | Address to listen for publish QUIC   | No       | [::]:38371            |
| `graphql_srv_addr`     | Giganto's GraphQL address            | No       | [::]:8443             |
| `data_dir`             | Path to directory to store data      | No       | data                  |
| `retention`            | Retention period for data            | No       | 100d                  |
| `oplog_retention`      | Retention period for operation logs  | No       | 365d                  |
| `export_dir`           | Path to Giganto's export file        | No       | export                |
| `max_open_files`       | Max open files for database          | No       | 8000                  |
| `max_mb_of_level_base` | Max MB for RocksDB Level 1           | No       | 512                   |
| `num_of_thread`        | Number of background threads for DB  | No       | 8                     |
| `max_subcompactions`   | Number of sub-compactions allowed    | No       | 2                     |
| `ack_transmission`     | Ack count for ingestion data         | No       | 1024                  |
| `compression`          | Enable RocksDB compression           | No       | false                 |
| `peer_srv_addr`        | Address to listen for peer QUIC      | No       | -                     |
| `peers`                | List of peer addresses and hostnames | No       | -                     |

<!-- markdownlint-enable MD013 -->

Relative `data_dir` and `export_dir` paths resolve against the process's working
directory. When `data_dir` is omitted, Giganto creates the default `data`
directory at startup. An explicitly configured `data_dir` must already exist.
The export directory is created on the first export.

Saving a changed configuration through `updateConfig` writes `data_dir` to the
configuration file, even when it was originally omitted. It then counts as an
explicit path and must already exist on subsequent starts.

The following is an example of how to configure the config file:

```toml
ingest_srv_addr = "0.0.0.0:38370"
publish_srv_addr = "0.0.0.0:38371"
graphql_srv_addr = "127.0.0.1:8443"
data_dir = "tests/data"
retention = "100d"
oplog_retention = "365d"
export_dir = "/opt/clumit/var/giganto/export"
max_open_files = 8000
max_mb_of_level_base = 512
num_of_thread = 8
max_subcompactions = 2
ack_transmission = 1024
peer_srv_addr = "10.10.11.1:38383"
peers = [ { addr = "10.10.12.1:38383",
            hostname = "001.giganto.node1.example.test" } ]
```

The RocksDB validity ranges on 64-bit targets are `max_open_files = 20..=C`,
`max_mb_of_level_base = 1..=262144`, `num_of_thread = 1..=128`, and
`max_subcompactions = 1..=8`. C is `max(20, min(soft RLIMIT_NOFILE, i32::MAX))`,
using the process soft open-file limit read once at startup; if reading it fails,
C is `4194304`. The thread caps are product policy limits. These ranges are
validity limits, not tuning recommendations.

At startup, out-of-range TOML values are clamped to the nearest bound, except
`max_open_files = -1`, which becomes C. One WARN per changed field reports the
file value, selected value, and valid range. The TOML is unchanged; RocksDB,
`--repair`, and the `config` query use the effective values. In-range values
are unchanged and produce no clamp warnings.

`updateConfig` rejects out-of-range values, including negative `max_open_files`,
without changing state or queuing the request. After an accepted update, a failure
in compression metadata validation, data directory migration, or database opening
logs an ERROR, restores the previous in-memory and persisted configuration, and
restarts with it once. The restore does not overwrite the update backup. If the
restore write fails, an ERROR asks that the file be checked and the previous
in-memory configuration still starts. A failure of that restored generation,
initial process startup, teardown, or startup after store opening is not recovered.
Check the effective outcome with the `config` query.

For the `max_mb_of_level_base`, the last level has 100,000 times capacity, and
it is about 90% of total capacity. Therefore, about `db_total_mb / 111111` is
appropriate. For example, 90 MB or less for 10 TB Database, 900 MB or less for
100 TB would be appropriate.

These values assume you've used all the way up to level 6, so the actual values
may change if you want to grow your data further at the level base. So if it's
less than 512 MB, it's recommended to set default value of 512 MB.

If there is no `peer_srv_addr` option in the configuration file, it runs in
standalone mode, and if there is, it runs in cluster mode for P2P.

### Database Compression Metadata

Giganto stores the compression setting in a metadata file named `COMPRESSION`
within the database directory (specified by `data_dir`). This file tracks
whether RocksDB compression is enabled or disabled for the database.

On startup, Giganto validates that the current `compression` configuration
matches the setting stored in the `COMPRESSION` metadata file. If there is a
mismatch, Giganto will report an error and refuse to start. This prevents data
corruption or access issues that could result from changing the compression
scheme of an existing database.

**Important**: Once a database is created with a specific compression setting,
changing the `compression` configuration option is not supported. If you need to
change the compression setting, you must recreate the database.

## Documentation

- Manual entry point: `docs/en/index.md` (English)
- 매뉴얼 시작점: `docs/ko/index.md` (한국어)

For detailed architecture, installation, configuration, and operations
guides, refer to the manuals above.

Build locally:

```bash
brew install python gh
python3 -m venv .venv
# zsh/bash:
source .venv/bin/activate
# fish:
source .venv/bin/activate.fish
pip install mkdocs-material mkdocs-static-i18n mkdocs-with-pdf PyYAML
scripts/fetch-theme.sh
mkdocs serve -a 127.0.0.1:8000 --livereload --dirtyreload
```

Command notes:

- `brew install python gh`: installs Python and the GitHub CLI (one-time
  per machine).
- `python3 -m venv .venv`: creates a local virtualenv for this repo.
- `source .venv/bin/activate`: activates the virtualenv for the
  current shell.
- `pip install ...`: installs MkDocs tooling into the virtualenv.
  Run once after creating the virtualenv (per clone).
- `scripts/fetch-theme.sh`: fetches the shared docs-theme assets
  into `docs/.theme/`. Requires the [GitHub CLI (`gh`)](https://cli.github.com/)
  and `tar`. Run once after cloning or when `docs/theme.toml` is updated.
- `mkdocs serve -a 127.0.0.1:8000 ...`: runs a local docs server.
- `mkdocs build`: builds static files into `site/`.
- `pip install mkdocs-material mkdocs-static-i18n mkdocs-with-pdf PyYAML`:
  installs the additional Python packages required for PDF builds.
- `brew install cairo pango gdk-pixbuf libffi`: installs the native
  dependencies required for PDF generation on macOS.
- `./scripts/build-docs-pdf.sh en|ko`: builds PDF manuals.

## Development

### Generating GraphQL Schema

To generate the GraphQL schema file, use the `gen_schema` binary:

```sh
cargo run --bin gen_schema --no-default-features
```

This command reads the GraphQL API definitions and exports the schema to
`src/graphql/client/schema/schema.graphql`.
